# Day 02 - K6 Performance Practice

Ngày: 2026-05-14

Mục tiêu hôm nay:

- Hiểu rõ hơn lỗi `4xx` khi load test checkout endpoint.
- Biết tạo diagnostic script để phân loại lỗi.
- Biết dùng `constant-arrival-rate` để kiểm soát request rate.
- Biết đặt threshold theo từng scenario.
- Biết viết kết luận performance ngắn, có số liệu.

## Bài 1: Diagnostic status code

Tạo file:

```text
scripts/checkout-diagnostic-test.js
```

Yêu cầu:

- Gọi `CHECKOUT_URL` giống `checkout-load-test.js`.
- Thêm counter cho các status cụ thể:
  - `checkout_status_200`
  - `checkout_status_400`
  - `checkout_status_401`
  - `checkout_status_403`
  - `checkout_status_404`
  - `checkout_status_409`
  - `checkout_status_429`
  - `checkout_status_5xx`
- Chạy với `10 VUs` trong khoảng `2m`.
- Xuất summary:

```powershell
k6 run -e CHECKOUT_URL=https://your-checkout-url --summary-export results/checkout-diagnostic-summary.json scripts/checkout-diagnostic-test.js
```

Câu hỏi cần trả lời:

- Lỗi `4xx` chủ yếu là status nào?
- Có phải `429 Too Many Requests` không?
- Có xuất hiện `5xx` không?

## Bài 2: Log lỗi có kiểm soát

Cập nhật diagnostic script để log tối đa 10 lỗi đầu tiên.

Gợi ý:

```js
import { Counter } from 'k6/metrics';

const loggedErrors = new Counter('logged_errors');
```

Yêu cầu:

- Chỉ log khi `response.status !== 200`.
- Log gồm:
  - status
  - duration
  - 200 ký tự đầu của body
- Không log toàn bộ body nếu response quá dài.

Câu hỏi cần trả lời:

- Body lỗi nói gì?
- Lỗi do token/session, rate limit, bot protection hay page không tồn tại?

## Bài 3: Request-rate test

Tạo file:

```text
scripts/checkout-rate-test.js
```

Dùng executor `constant-arrival-rate`.

Profile đề xuất:

```js
export const options = {
  scenarios: {
    checkout_rate: {
      executor: 'constant-arrival-rate',
      rate: 5,
      timeUnit: '1s',
      duration: '2m',
      preAllocatedVUs: 20,
      maxVUs: 50,
    },
  },
};
```

Yêu cầu:

- Chạy lần 1 với `rate: 5`.
- Chạy lần 2 với `rate: 10`.
- Chạy lần 3 với `rate: 20`.
- Mỗi lần xuất summary riêng:

```powershell
k6 run -e CHECKOUT_URL=https://your-checkout-url --summary-export results/rate-5-summary.json scripts/checkout-rate-test.js
```

Câu hỏi cần trả lời:

- Rate nào bắt đầu xuất hiện lỗi rõ rệt?
- `p95` tăng hay lỗi tăng trước?
- Endpoint fail do latency hay do rejection `4xx`?

## Bài 4: Threshold theo lỗi thực tế

Sau khi biết loại lỗi chính, đặt threshold phù hợp hơn.

Ví dụ:

```js
thresholds: {
  http_req_failed: ['rate<0.02'],
  http_req_duration: ['p(95)<1000'],
  checks: ['rate>0.98'],
}
```

Yêu cầu:

- Nếu endpoint có rate limit, không đặt threshold quá thấp khi dùng chung một checkout URL.
- Nếu mục tiêu là page availability, status `200` phải là check bắt buộc.
- Nếu mục tiêu là backend latency, cần tách riêng lỗi business rule và lỗi server.

Câu hỏi cần trả lời:

- Threshold hiện tại có phản ánh đúng mục tiêu test không?
- Threshold nào nên dùng cho smoke, load, stress?
